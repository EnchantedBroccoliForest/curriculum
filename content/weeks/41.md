# Week 41: Question and falsifier; protocol

## Why this week

The capstone demonstrates method, not a result: one bounded investigation inside what Phases 1–3 covered, specified by you, executed by an agent, audited by you, and defended orally. This week fixes the question and the protocol before anything is run, so that weeks 42–44 test a commitment rather than a story written after the data arrived. An analytical capstone (a technical-report audit or a cost-and-decision analysis with a small simulation) is equally acceptable and fits a founder's use better than a training run.

## Objectives

- Write a one-page question with a falsifier: a concrete observation that, if seen, would make you abandon the claim.
- Complete every field of the protocol below before any agent run, and freeze it (hash or dated copy).
- State the budget (under $300 or none) and a stopping rule that does not depend on whether the result looks favourable.

## Key ideas

- A claim without a falsifier is not a hypothesis. Write the falsifier as a threshold on the pre-specified metric, not as a feeling.
- Pre-registration: the unit of analysis, splits, metric, baseline and analysis are fixed before data. Anything decided afterwards is exploratory and is labelled so in the write-up.
- Paired comparisons: baseline and treatment on the same items, difference per item, uncertainty from the paired differences (bootstrap or a paired test). Report the interval, not only the mean.
- Cost per successful task is the metric a founder uses; raw accuracy hides the denominator. Define success and cost before running.
- If retrieval is involved, separate retrieval failure from generation failure in the metric design (week 37), and fix an abstention policy and how abstentions are scored.
- Baseline strength: the strongest cheap alternative, not a straw man. Matched budgets: same model, same token or dollar budget, same test set untouched.
- Apply the six judgment questions (contamination, baseline strength, matched budgets, seed variance, judge reliability, construct validity) to your own protocol before anyone else does.
- Stopping rule: a fixed sample size or a fixed budget, set now. Optional stopping on a favourable interim result inflates the false-positive rate.

## Derivation or exercise, stated in full

Unit of analysis, splits, metric, baseline, stopping rule, budget (under $300 or none)

Protocol template. Fill every field; a blank field means the protocol is not finished.

1. **Question** (one sentence, answerable yes/no or by a number with an interval): …
2. **Claim and falsifier**: the claim is …; the result that would refute it is … (a threshold on the metric below).
3. **Unit of analysis** (what one data point is: a prompt, a document, a run, a model pair): …
4. **Population and sampling**: where the units come from, how many, how sampled, what is excluded and why.
5. **Splits**: development set (for prompt and pipeline iteration) and test set (untouched until the final run), with sizes and how the test set is sealed.
6. **Metric**: definition, how it is computed, who or what computes it (if an LLM judge: its prompt, its reliability check against hand labels on n items).
7. **Baseline**: the strongest cheap alternative, run under the same budget on the same units.
8. **Treatment(s)**: what differs from the baseline, and nothing else.
9. **Analysis plan**: paired differences; uncertainty method (bootstrap with B resamples, or named test); number of seeds or repeats; the one pre-specified primary comparison.
10. **Stopping rule**: fixed n = … or fixed budget = …; no interim peeking at the primary metric.
11. **Budget**: under $300 or none; estimated cost per run; total runs allowed.
12. **Pre-registration**: date, file hash or snapshot of this protocol; anything changed afterwards is listed in the write-up as a deviation.

<details>
<summary>Hints</summary>

- If you cannot write the falsifier, the question is too vague; narrow the population or the metric until a refuting observation is nameable.
- Compute the paired-difference standard error you would need to detect the smallest effect you care about; if the sample size that implies is beyond budget, shrink the question rather than the uncertainty.
- The baseline should be the thing a competent team would ship without your idea.

</details>

## Self-check

1. State your falsifier as a number on your metric. Could the agent's run produce that number? If not, why not?
2. What is one data point in your study, and how many of them do you have in the sealed test set?
3. What decision would a founder make differently if the result is positive versus negative? If the answer is "nothing", reconsider the question.

## Common misconceptions

- "A bigger test set fixes everything." Correct: it narrows the interval; it does nothing about contamination, a weak baseline, or a metric that does not measure the construct.
- "The protocol can be adjusted once I see early results." Correct: it can, but every adjustment after data is a deviation to be reported, and the primary comparison is the one registered now.
- "An analytical capstone is the easy option." Correct: a report audit or cost analysis has the same requirements (falsifier, uncertainty, alternative explanations) and its data is harder to clean.
