# Week 25: DeepSeek-V4 report: training-budget audit

## Why this week

This is the Gate 2 report audit: every FLOP, byte and dollar in a training run accounted for on paper, with each number labelled by where it came from. It is the exit condition of Phase 2 and the skill a founder uses on any vendor's technical report. The method, not the particular report, is what [week 27](/week/27) tests closed-book and the [week 41](/week/41) capstone may reuse.

## Objectives

- Reconstruct a training budget (tokens, FLOPs, GPU-hours, dollars) from a technical report with every number labelled reported, derived, or unknown.
- For each derived number, write the formula and the reported inputs it used, so a reader can recompute it.
- State which claims in the report cannot be checked from the report alone and what external information would be needed.

## Key ideas

- Three labels, kept separate. Reported: a number printed in the report. Derived: computed from reported numbers by a stated formula. Unknown: needed for the budget but absent; you may bound it, never fill it in silently.
- Training FLOPs: $C \approx 6 N_{\text{active}} D$ for a dense or routed transformer with $D$ training tokens, plus the attention term $\approx 12\, L\, s\, d_{\text{model}}\, D$ for $L$ layers, sequence length $s$; state whether you include it and whether the report does.
- GPU-hours follow from FLOPs, peak hardware throughput, and model FLOP utilisation (MFU): $\text{hours} = C / (\text{peak FLOP/s} \times \text{MFU} \times 3600 \times n_{\text{GPU}})$. MFU is usually the unknown; reports that give GPU-hours let you solve for it.
- Dollars need a price per GPU-hour, which no report fixes; give a range and label it as an assumption.
- Memory per device during training: weights, gradients, optimizer state (two moments for Adam) and activations, each at its own precision, divided by the parallel degrees. Mixed precision means weights may exist in two copies.
- Multiple training stages (pretraining, long-context extension, mid-training, post-training) each carry a token count and a cost; a headline cost that covers only one stage is a reporting choice to flag.
- Numbers that depend on undisclosed data (token count per stage, MFU, cluster size over time) stay unknown even when a plausible value is obvious.

## Common misconceptions

- "The report's headline cost is the cost of the model" → It is the cost of the stages the report chose to price, at a GPU price the report assumed.
- "Derived numbers are as reliable as reported ones" → They inherit the uncertainty of every input and of the formula's assumptions, such as whether attention FLOPs are counted.
- "If a value is obvious it can be filled in" → An obvious value is still unknown in the report; recording it as an assumption keeps the audit honest.
