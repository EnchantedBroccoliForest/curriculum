# Week 20: CS336: GPUs; parallelism (overview)

## Why this week

A 7B model does not fit on one GPU for training once optimizer state and activations are counted, so every training run is a parallelism decision. This week is read-only at the systems level: enough to account for memory per GPU under the three basic schemes, which Gate 2 (week 27) tests closed-book. Read the collectives appendix first; all-reduce, all-gather and reduce-scatter are the vocabulary.

## Objectives

- Write the per-GPU memory of mixed-precision training as a sum of weights, gradients, optimizer state and activations, with bytes per parameter for each.
- State how data, tensor and pipeline parallelism each divide those terms, and what communication each adds.
- Evaluate the memory per GPU for a 7B model under each scheme and a given degree of parallelism.

## Key ideas

- Mixed-precision Adam holds bf16 weights and gradients plus fp32 master weights and two fp32 moments: about 16 bytes per parameter before activations. For 7B parameters that is far above a single accelerator's memory.
- Activation memory scales with batch, sequence length, layers and width; activation checkpointing trades it for recomputation (about a third more forward FLOPs).
- Data parallelism replicates the model and splits the batch; gradients are all-reduced each step. ZeRO stages shard optimizer state, gradients and weights across the data-parallel group, turning the all-reduce into reduce-scatter plus all-gather.
- Tensor parallelism splits individual matmuls across devices; it needs an all-reduce per layer and so wants the fastest interconnect (within a node).
- Pipeline parallelism splits layers across devices and introduces bubbles; micro-batching shrinks the bubble at the cost of activation memory for in-flight micro-batches.
- The roofline picture from week 3 applies to communication too: a collective is bandwidth-bound, and its cost is bytes moved over link bandwidth.

## Derivation or exercise, stated in full

Memory per GPU under data, tensor, and pipeline parallelism for a 7B model

Setting: a dense 7B-parameter decoder, bf16 compute with fp32 master weights and Adam, sequence length and micro-batch size of your choosing (state them), 8 GPUs. For each of (a) pure data parallelism without sharding, (b) data parallelism with full optimizer-state and gradient sharding, (c) tensor parallelism of degree 8, (d) pipeline parallelism of degree 8 with a stated number of micro-batches: write the per-GPU memory as a formula with separate terms for weights, gradients, optimizer state and activations, then evaluate it. State the activation-memory formula you use and whether checkpointing is on. Give the communication volume per step for each scheme in bytes as a formula. No numeric answers are supplied here; the Ultra-Scale Playbook's parallelism chapter has the reference formulas to check against.

2. Why is tensor parallelism kept within a node while pipeline parallelism crosses nodes?
3. If activation checkpointing is enabled, what happens to FLOPs per step and to the compute-versus-memory trade-off?

## Common misconceptions

- "Model memory equals parameters times two bytes." → That is inference in bf16; training with Adam is about eight times that before activations.
- "More parallelism always reduces memory per GPU." → Pipeline parallelism adds in-flight activation memory and bubbles; the degree is a trade, not a free reduction.
