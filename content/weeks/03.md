# Week 3: PyTorch blitz; CS336 lectures: PyTorch and einops; GPUs and TPUs

## Why this week

From here on, every training script you read is PyTorch: tensors with shapes, modules holding parameters, an optimizer stepping them, autograd doing what micrograd did. Rewriting micrograd's MLP and matching its loss curve proves the mapping is exact. The roofline for one GPU is the cost model used in every FLOP and memory estimate from [week 9](/week/9) through Gate 2 ([week 27](/week/27)).

## Objectives

- Rewrite the week-2 MLP in PyTorch and reproduce its loss curve to within numerical noise given the same initial parameters and data order.
- Read a `torch.einsum` or einops expression and write out the summation it performs, and the reverse.
- Draw the roofline for one named GPU from its datasheet and place a matmul and an elementwise operation on it.

## Key ideas

- A **tensor** is an $n$-dimensional array with a dtype, a device (CPU or GPU) and, if `requires_grad`, a place in the autograd graph. Operations record a graph; `loss.backward()` runs reverse mode exactly as micrograd does, with gradients accumulated into `.grad`, hence `optimizer.zero_grad()` before each step.
- `nn.Module` groups parameters and a `forward` method; `nn.Linear(d_in, d_out)` holds $W \in \mathbb{R}^{d_{out} \times d_{in}}$ and $b$, computing $xW^\top + b$. An **optimizer** (`torch.optim.SGD`, `Adam`) owns the update rule; the loop is forward, loss, `backward`, `step`, `zero_grad`.
- **einsum / einops** name axes instead of relying on position: `einsum("bij,bjk->bik", A, B)` is a batched matmul; einops `rearrange(x, "b (h d) -> b h d", h=8)` splits a dimension. Named axes make the shape bookkeeping of attention ([week 9](/week/9)) checkable by reading.
- Matching a loss curve requires the same initialisation, the same data order and the same arithmetic precision; the comparison is the loss trajectory, not the final value alone, and differences at the $10^{-6}$ level are rounding ([week P3](/week/P3)).
- A **GPU** executes kernels over many threads; memory is HBM with bandwidth $\beta$ bytes/s and peak throughput $\pi$ FLOP/s for a given dtype (tensor cores give a much higher $\pi$ for fp16/bf16 matmul than for fp32). A **TPU** has the same roofline structure with a systolic array in place of streaming multiprocessors.
- **Roofline**: for a kernel with arithmetic intensity $I = F / B$ flop per byte, attainable throughput is $\min(\pi,\; \beta I)$; the ridge point is $I^* = \pi / \beta$. A matmul of $n \times n$ matrices has $I \approx n / 3$ (fp16: $2n^3$ flops over $6n^2$ bytes), compute-bound once $n$ exceeds a few hundred; elementwise ops have $I \lesssim 1$ and are memory-bound regardless of size.
- Kernel launch overhead and Python dispatch are a third ceiling for small tensors; it is why tiny models are not a faithful benchmark of the hardware.

## Derivation or exercise, stated in full

micrograd's MLP in PyTorch, loss curve matched; roofline for one GPU

1. **MLP in PyTorch.** Reimplement the [week 2](/week/2) MLP with `nn.Module` and `nn.Linear`, tanh activations and squared-error loss. Copy the micrograd initial weights into the PyTorch parameters, use the same batch and learning rate, run the same number of steps with plain SGD, and plot both loss curves on one axis. Report the maximum absolute difference between the two curves and attribute it.
2. **einops.** Rewrite the forward pass of one layer with `torch.einsum`, and write the index-sum formula that the expression denotes.
3. **Roofline for one GPU.** Choose one GPU (state the model). From its datasheet take $\pi$ for bf16 or fp16 tensor-core matmul, $\pi$ for fp32, and $\beta$ for HBM. Draw the roofline (log-log, intensity on the x-axis, attainable FLOP/s on the y-axis), compute the ridge point, and place on it: a $4096^2$ fp16 matmul, a $256^2$ fp16 matmul, and an elementwise `tanh` over $10^8$ elements. State for each whether it is compute- or memory-bound and the attainable time.

Assumptions: single GPU or CPU for part 1 (the matching is about arithmetic, not speed); datasheet figures are peak values and should be labelled as such.

## Common misconceptions

- PyTorch autograd is a different mechanism from micrograd's → it is the same reverse-mode recurrence over a recorded graph, with tensor-valued nodes and vector-Jacobian products in compiled kernels.
- A GPU's advertised FLOP/s is what a model achieves → attainable throughput is $\min(\pi, \beta I)$; most kernels outside large matmuls sit on the bandwidth roof.
- Two loss curves that differ in the sixth decimal indicate a bug → at that scale the difference is summation order in floating point; a bug shows as divergence that grows with steps.
