# Week 18: CS336: tokenization; architectures and hyperparameters

## Why this week

Phase 2 is cost accounting, and every later count (KV-cache in week 19, memory per GPU in week 20, the training budget in week 25, Gate 2 in week 27) starts from the parameter count and per-token FLOPs you derive here. Tokenization is where the data enters the model and where perplexity comparisons across models silently break.

## Objectives

- Run byte-pair-encoding merges by hand on a short corpus and state what the merge table and vocabulary are at each step.
- Count the parameters of nanochat's model from its config and derive the forward FLOPs per token, then check both against the code.
- Explain how RoPE encodes relative position through a rotation of query and key, and why that matters for context extension.

## Key ideas

- BPE: start from bytes, repeatedly merge the most frequent adjacent pair, record the merge order; encoding applies merges in that order. Vocabulary size trades sequence length against embedding and output-layer size.
- For a dense decoder with $L$ layers, width $d$, MLP width $d_{\text{ff}}$ and vocabulary $V$: parameters are roughly $L(4d^2 + 2 d\, d_{\text{ff}}) + V d$ (tied embeddings), with the exact constant depending on biases, gated MLPs and GQA. Write the formula for nanochat's actual choices, not the textbook one.
- Forward FLOPs per token are about $2 \times$ (non-embedding parameters) plus the attention term $\sim 4 L T d$ that depends on context $T$; training is about three times the forward cost. This is the origin of $C \approx 6ND$.
- RoPE applies a position-dependent rotation to $q$ and $k$ in 2-d subspaces so that $\langle q_m, k_n\rangle$ depends on $m-n$; the base frequency controls the wavelengths and is what context-extension methods rescale.
- Architecture choices in CS336 (pre-norm, RMSNorm, SwiGLU, GQA, no biases) are hyperparameters with cost consequences; each changes the count above by a term you can name.
- Perplexity is per token, so two models with different tokenizers are not comparable on it without converting to bits per byte.

## Derivation or exercise, stated in full

BPE merges by hand (Karpathy's tokenization video as the guide); parameter count and per-token FLOPs of nanochat's model, checked against the code

Part 1. Take a corpus of about 30 bytes of your choosing. Perform five BPE merges by hand, writing the pair counts, the chosen merge and the resulting token sequence after each. Then encode a new short string with the resulting merge table, applying merges in training order.

Part 2. From nanochat's model configuration, write the parameter count as a formula in $L$, $d$, $d_{\text{ff}}$, number of query heads, number of key-value heads, head dimension and $V$, and evaluate it. Then write forward FLOPs per token as a formula in the same quantities plus context length $T$, separating the parameter-proportional term from the attention term. State which quantities are reported in the config and which you derived. Finally check both against the code (count the parameters programmatically; read the matmul shapes) and reconcile any difference.

## Common misconceptions

- "Parameter count determines compute." → Compute per token also has an attention term proportional to context; at long context it dominates.
- "RoPE adds a position vector to the input." → RoPE rotates queries and keys inside attention; nothing is added to the residual stream.
