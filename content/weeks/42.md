# Week 42: Agent runs baseline and experiment

## Why this week

The agent executes the week-41 protocol; you audit it. The skill being exercised is the one a founder uses weekly: specifying work for an agent and verifying its execution without redoing it. The audit log produced here is a checkpoint artifact and the evidence base for the week-43 write-up and the week-44 defence.

## Objectives

- Run the baseline and the treatment to the frozen protocol, with every run recorded in the audit log below.
- Hand-check the metric on a random sample of raw outputs and reconcile every discrepancy with the agent's computed metric.
- Produce a complete audit log with no empty cells and every deviation from the protocol recorded.

## Key ideas

- The agent's reported metric is a claim, not a measurement, until you have recomputed it on raw outputs yourself.
- Audit raw outputs, not summaries: open the actual generations, the actual retrieved passages, the actual judge verdicts.
- Hand-check a random sample sized in advance (for example 30 items per arm); if the discrepancy rate exceeds a pre-set threshold, recompute the whole metric by hand or by independent code.
- Hash the inputs and pin versions (model identifier, prompt or spec version, seed) so a run can be identified and reproduced.
- Retries and reruns are data: log them; a result that depended on rerunning until it passed is a different result.
- Separate retrieval failure from generation failure per item where retrieval is involved; count abstentions under the registered policy.
- Stay within budget; log cost per run and cost per successful task.
- An analytical capstone follows the same log, with "run" replaced by "extraction" or "simulation batch" and the hand-check applied to the extracted numbers.

## Derivation or exercise, stated in full

Audit raw outputs; hand-check metric calculations

Audit-log format, one row per agent run (baseline and treatment arms alike, including aborted runs and reruns):

| Timestamp | Arm | Prompt/spec version | Inputs hash | Outputs location | Metric (agent) | Metric (hand-checked) | Discrepancy | Cost | Decision |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| ISO 8601 | baseline / treatment | git hash or version tag | sha256 of the input set | path or URL | value with n | value on sampled items with n | absolute and relative | $ | accept / rerun (reason) / discard (reason) |

Hand-check procedure:

1. Before looking at any metric, draw a random sample of items per arm with a recorded seed (size fixed in the protocol).
2. For each sampled item, score it yourself from the raw output using the registered metric definition; record the score next to the agent's.
3. Compute the discrepancy rate; if it exceeds the threshold set in week 41, recompute the full metric independently and record both values.
4. For LLM-judge metrics, record judge agreement with your labels on the sample; an agreement rate below the registered floor invalidates the metric for that run.
5. Record every deviation from the protocol (changed prompt, changed sample, rerun) in the Decision column with its reason.

<details>
<summary>Hints</summary>

- Scoring blind to the arm label removes the obvious bias in your own hand checks.
- The discrepancy column exists for the cases where the agent's code computed the right number on the wrong items (leakage from development to test set is the common one).
- Keep the sealed test set sealed: the agent should not be able to read it during pipeline iteration.

</details>

## Self-check

1. For one run, reproduce the agent's metric from its raw outputs without its code. Did you get the same number? If not, which cell of the log explains why?
2. How many items did you hand-check, and what discrepancy rate would have triggered a full recomputation?
3. Which runs in your log were reruns, and does the primary result survive if the first attempts are used instead?

## Common misconceptions

- "The agent's summary table is the result." Correct: the result is the hand-checked metric on raw outputs; the summary is an input to the audit.
- "Reruns are noise and can be dropped." Correct: reruns are logged and reported; selectively keeping successful reruns is the mechanism by which results become unreproducible.
- "A sample of 5 is enough to check the metric." Correct: the sample size is fixed in advance from the discrepancy rate you need to detect, not chosen for convenience.
