# Week 32: CS336: mid- and post-training; RLVR

## Why this week

The CS336 post-training material and the Tülu 3 report give the full recipe that sits between a pretrained base and a deployed model: SFT, preference tuning, then reinforcement learning with verifiable rewards (RLVR). Weeks 33–35 derive and stress the RLVR estimator; this week fixes what the stage is claimed to do and how the claim was tested. The ablation-reading habit here is the one the week-39 benchmark critique and the capstone audit depend on.

## Objectives

- Name the stages of the Tülu 3 pipeline in order and state, for each, the data it consumes and the objective it optimizes.
- Given one Tülu 3 ablation table, state which benchmark deltas are attributable to the RLVR stage alone and which are confounded by data or decoding changes.
- Write a one-paragraph account of what "verifiable reward" means operationally (what function of the output is computed, by what program) for the task families in the report.

## Key ideas

- Mid-training versus post-training: the former changes the data mixture while continuing the pretraining objective; the latter changes the objective. The distinction matters because a benchmark gain from mid-training data is not evidence about the RL algorithm.
- RLVR replaces a learned reward model with a program: an answer checker, a unit test, a format verifier. The reward is $r(o) \in \{0, 1\}$ (or a small set), which removes reward-model drift but restricts the task distribution to what can be checked.
- The policy objective is still the KL-regularized one of week 28, $\max_\pi \mathbb{E}_{o \sim \pi}[r(o)] - \beta\, \mathrm{KL}(\pi \,\|\, \pi_{\text{ref}})$; the estimator used (PPO or GRPO) is the week-29 and week-34 material. RLVR is a choice of reward, not a new algorithm.
- An ablation isolates one stage only if everything else is held fixed: same SFT checkpoint, same evaluation prompts, same decoding settings, same number of seeds. The report's tables should be read column by column for exactly these conditions.
- A benchmark that is itself verifiable (exact-match math, executable code) is the same kind of object as the RLVR training signal; a gain there can be partly an in-distribution effect. Transfer to non-verifiable tasks is the harder claim.

## Common misconceptions

- "RLVR is a new RL algorithm." → RLVR names the reward source (a verifier); the optimizer is PPO or GRPO, unchanged from the preference-tuning setting.
- "A gain on GSM8K after RLVR on math prompts shows reasoning improved." → It shows in-distribution performance on a verifiable task improved; the transfer claim needs a held-out, non-overlapping task family.
- "Mid-training and post-training can be read from the same ablation." → They change different things (data versus objective); a table that varies both at once cannot attribute the delta.
