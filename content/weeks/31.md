# Week 31: Practitioner stack: quantization, serving, merging

## Why this week

This is the practitioner layer added from Labonne's course: what a team of yours would do to shrink, serve and combine a model, and what each choice costs. Lecture level with one guided run; nothing is derived. It closes the cost thread from [week 26](/week/26) and supplies the serving numbers the agent build in [week 38](/week/38) will need.

## Objectives

- Compute the weight memory of a 7B model at fp16, int8 and int4, including the overhead of quantisation scales, and state what else occupies memory at serving time.
- Quantise a small model to GGUF and report perplexity against bits per weight as a measured curve, with the evaluation set named.
- Write one page choosing a serving stack for a stated workload and pricing it per million tokens.

## Key ideas

- Weight memory is parameters × bytes per weight plus per-block scale (and zero-point) overhead; at int4 with a block size of 32 the overhead is not negligible. KV cache and activations are extra and scale with batch and context.
- absmax quantisation maps $[-\max|w|, \max|w|]$ onto the integer range; zero-point quantisation maps $[\min w, \max w]$; both are per-tensor or per-block, and the block size sets the accuracy–overhead trade.
- Outlier channels break naive quantisation of activations; LLM.int8, SmoothQuant, GPTQ and AWQ are different answers to where the error is pushed (mixed precision, scaling into weights, error-compensating rounding, salience-weighted scaling). Lecture level: mechanism and trade-off, not reproduction.
- Perplexity versus bits is the measured curve that tells you where quality drops; it depends on the model, the calibration data and the evaluation set, so a published curve transfers only approximately.
- Serving options differ along: local runner for one user (llama.cpp, Ollama, LM Studio) versus batched server (vLLM, TGI); cost is GPU-hours over tokens served at the utilisation you actually reach, not at the benchmark peak.

## Derivation or exercise, stated in full

Memory of a 7B model at fp16, int8, int4 by hand; quantize a small model to GGUF (AutoQuant Colab or llama.cpp) and measure the perplexity change against bits; one page: the serving stack a team of yours would pick, and the cost per million tokens of each option

Part 1. For a 7B-parameter model, compute weight memory at fp16, int8 and int4: parameters × bytes plus scale overhead for a block size you state; add, as separate lines, KV-cache memory for a stated context and batch and the runtime's activation working set; say what fits on a GPU of a stated size. Part 2. Quantise one small open model to GGUF at three or more bit widths with the AutoQuant Colab or llama.cpp; measure perplexity on one named evaluation text for each and for the unquantised baseline; tabulate bits per weight, file size, perplexity and tokens per second on your hardware. Part 3. One page: for a workload you specify (requests per second, context length, latency target, users), choose between a local runner and a batched server, name engine and precision, estimate cost per million tokens from GPU price, throughput and expected utilisation, and list what would change the decision.

## Self-check

1. Why is "4-bit" not 4 bits per weight in practice, and what sets the gap?
2. A benchmark reports 2,000 tokens per second on a GPU for your model. What utilisation assumption turns that into a cost per million tokens, and why is the real figure usually worse?
3. Which quantisation methods act on weights only and which also address activations?

## Common misconceptions

- "Quantising to int4 cuts memory by exactly 4× versus fp16" → Scales, zero-points, un-quantised layers, KV cache and activations keep the real ratio lower.
- "The cheapest engine per benchmark token is the cheapest to run" → Cost follows the utilisation you achieve at your traffic pattern and latency target.
