# Week 26: CS336: inference

## Why this week

Inference is where the dollars are spent after training, and its arithmetic is different: decode is memory-bandwidth-bound, so throughput depends on batching and KV-cache management, not on peak FLOP/s. This week closes the cost accounting Phase 2 set out to teach and feeds the serving-stack decision in [week 31](/week/31).

## Objectives

- Explain why single-stream decode is bandwidth-bound and how batching moves it toward compute-bound, using the roofline from [week 21](/week/21).
- Derive the expected speedup of speculative decoding as a function of draft length and acceptance rate, and state its assumptions.
- Estimate tokens per second per dollar for one open model on one GPU and reconcile the estimate with a published benchmark.

## Key ideas

- Prefill processes the prompt in parallel and is compute-bound; decode produces one token per forward pass and, at batch size 1, moves all weights through HBM per token, so time per token $\approx$ bytes of weights / bandwidth.
- Batching $B$ sequences amortises the weight read; arithmetic intensity grows with $B$ until the KV-cache reads, which scale with $B \times$ context, dominate. The KV cache is the binding memory term at high batch.
- Speculative decoding: a cheap draft model proposes $\gamma$ tokens, the target verifies them in one forward pass, and rejection sampling keeps the target's distribution exactly. Speedup depends on the per-token acceptance rate $\alpha$ and the draft-to-target cost ratio.

## Derivation or exercise, stated in full

Speedup vs acceptance rate; tokens per second per dollar for one open model on one GPU, checked against a published benchmark

Part 1. Assume a draft model proposing $\gamma$ tokens per step, each accepted independently with probability $\alpha$, and a target verification costing one target forward pass regardless of $\gamma$. Define the expected tokens produced per target step and the expected wall-clock speedup over plain decoding when the draft costs a fraction $c$ of a target step per token; state the independence assumption and when it fails. Part 2. Fix one open-weight model, one GPU, a precision, a context length and a batch size. From weight bytes, KV-cache bytes per token, HBM bandwidth and peak FLOP/s, estimate decode tokens per second and divide by an hourly price you state. Compare with one published serving benchmark for the same model and GPU; list every setting that differs from yours and the direction each pushes the number.

## Common misconceptions

- "Decode throughput is limited by FLOP/s" → At small batch it is limited by memory bandwidth; FLOP/s binds only once batching raises arithmetic intensity.
- "Speculative decoding changes the output distribution" → With the rejection-sampling verification rule the target distribution is preserved exactly.
